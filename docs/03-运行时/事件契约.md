# Agent 事件契约

跨端 TypeScript DTO 位于 `packages/contracts/agent.ts`、`packages/contracts/rag.ts`、`packages/contracts/team.ts`，renderer 通过 `@agentcore/contracts` 使用；这些文件是 wire 形状镜像，不替代 Python 运行时校验。

## 现有 SSE envelope

`apps/agent-runtime/desktop_api.py` 将事件持久化到 SQLite，并通过 `id`、query `after` 和标准 `Last-Event-ID` 支持回放：

```json
{
  "event_id": 42,
  "event_type": "tool.result",
  "turn_id": "turn-uuid",
  "payload": {},
  "created_at": 1780000000.12
}
```

SSE 线格式为 `id`、`event`、`data`；客户端断线后必须使用最后一个 `event_id` 继续读取，不得以时间戳猜测缺失事件。

`data` 只包含 `turn_id`、`payload`、`created_at`；`id` 是持久化事件的数值 cursor，`event` 是事件类型。轮询 JSON 使用 `PersistedStreamEvent`（`event_id`、`event_type`、`turn_id`、`payload`、`created_at`），renderer 再统一投影为 camelCase 的 `StreamEvent`。历史轮询可显式传 `summary=true`：仅 `tool.requested` 与 `tool.result` 的输入/输出会被截断为摘要，payload 标记 `_summary=true`、`_detail_event_id` 和 `_detail_available=true`；原始完整事件通过 `GET /api/v1/sessions/{session_id}/events/{event_id}` 按 session 内的事件 ID 读取。SSE 始终发送完整事件。未知 `event_type` 仍按字符串保存和回放，不能只依赖已知事件枚举。

当前 desktop renderer 由 `apps/desktop/.../services/agentEvents.ts` 统一建立 Agent SSE 连接，并以 750ms 轮询作为回放兜底；断线会携带当前 cursor 重建连接，两条路径共享同一个 cursor 和有界 event id 去重集合。Team 观测由 `useTeamObservation` 直接轮询 `/team/events` 的 SQLite 增量，并以返回的折叠快照作为权威状态；SSE 只提供低延迟补充。服务端长轮询在内存 deque 之外还会从 SQLite 补读，避免慢客户端漏事件。

首次历史轮询默认使用 `stream=false&summary=true&limit=<window>`，服务端只返回最近窗口，并带 `has_more_history`、`oldest_event_id` 和原始高水位 `latest_event_id`；renderer 以高水位建立 SSE，再按 `before=<oldest_event_id>` 分页加载较早历史。启动预热选中的热点会话会在 `/api/v1/sessions` 和会话详情中标记 `history_mode: "full"`，renderer 对这些会话首轮使用 `full_history=true`，一次加载完整的折叠历史并直接建立最新 cursor；冷会话继续使用窗口和按需分页。完整会话仍保留在 SQLite journal，历史没有被删除或截断。历史折叠保留用户消息、Agent 回复、工具和审批事件，将 `model.requested`、`turn.completed` 等低价值生命周期事件折叠进对应 `turn.finished.payload.lifecycle_summary`。工具详情仍在用户展开操作卡片时按 `_detail_event_id` 请求。`assistant.message` 可带 `phase=planning|finding|final`：前两者是用户可见的计划/发现摘要，`final` 才投影为答案消息；这不是私有思维链回放。

会话切换对热点会话读取完整折叠历史，对冷会话读取近期历史窗口并立即返回；`AgentRuntime` 由后台预热线程恢复，发送新回合时复用已就绪的运行时。API 启动后会优先预热运行中和最近更新的会话，数量由 `DESKTOP_WARM_SESSION_COUNT` 控制且不会超过 `DESKTOP_MAX_RUNTIME_SESSIONS`；热点历史全量读取在线程中执行，健康检查不等待。普通 `queue` 回合始终先以可选的 `request_id` 原子写入 SQLite、产生 `turn.queued`，随后由后台调度器恢复/唤醒 runtime；`POST /turns` 不等待 Git 基线、runtime 恢复或模型调用。重复 `request_id` 返回同一回合，`GET /api/v1/sessions/{session_id}/turns/{turn_id}` 可在客户端提交超时后确认状态。运行时恢复会重建必要的用户/Agent 对话上下文，skills 与 memory 不参与 renderer 的同步历史请求。Git 基线按规范化 workspace 路径在 `DesktopManager` 内共享，回合结束后异步刷新，回合账本仍按 session 独立维护。

最终答案支持增量传输：同一答案的 `assistant.message` 事件带相同的 `stream_id`，增量文本位于 `delta`（同时写入 `text` 兼容旧客户端），流式分片使用临时 `phase=streaming`，结束事件带 `stream_done=true`。当模型输出包含工具调用时，planning/finding 收尾事件仍带完整的 `text`，同时带 `stream_retracted=true`；renderer 应按 `stream_id` 从普通消息中删除已展示的临时片段，并将该收尾正文投影到执行轨迹，避免计划/发现内容闪现后丢失。模型重试或异常导致的 `phase=final` 临时文本仍按 `stream_retracted=true` 删除；不带 `stream_id` 的旧事件仍按完整答案处理。

## Agent Workspace HUD

renderer 的任务 HUD 按 `turn_id` 消费 durable Agent 事件：`todo_write` 的 `input.todos` 投影为步骤，`tool.requested` 与 `tool.result` 按 `tool_use_id` 聚合为命令、文件编辑、审查和请求卡片；旧执行轨迹不再逐条重复展示底层工具事件。

代码变更事实来自 desktop facade，而不是 renderer 直接读取工作树。回合终止事件会附带该回合最终 `changes` 快照，使历史答案可以恢复自己的变更账本，而不读取后续回合的工作树状态：

- `turn.finished.payload.changes` 或 `turn.error.payload.changes` 包含 `files`、`total_files`、`total_additions`、`total_deletions` 及文件 diff 信息。

代码变更事实接口仍包括：

- `GET /api/v1/sessions/{session_id}/changes` 返回文件路径、增删统计和 diff hunk 行号锚点。
- `POST /api/v1/sessions/{session_id}/changes:review` 创建一次本地 Code Review 请求标识，并返回当前变更快照。
- `POST /api/v1/sessions/{session_id}/changes:revert` 只回滚会话初始化时尚未 dirty 的路径；用户原有 dirty 文件会列在 `protected_paths` 中，不执行 `git checkout -- .`。

HUD 变更同步使用短轮询补充事件流，缺少 Git 工作树时仍保留操作摘要，不把文件统计伪装成可用事实。

## 当前已落地事件

`session.created`、`turn.queued`、`turn.started`、`user_interjection`、`model.requested`、`assistant.message`、`tool.requested`、`tool.result`、`approval.requested`、`approval.resolved`、`turn.cancel.requested`、`turn.cancelled`、`turn.finished`、`turn.error`、`video.progress`、`video.failed`，以及 `run.plan`、`run.started`、`run.progress`、`run.completed`、`run.failed`。

`user_interjection` 表示当前运行回合收到用户的 steer 追加消息。payload 至少包含 `interjection_id` 和 `status`，状态含义如下：

| 状态 | 含义 |
| --- | --- |
| `received` | 已完成确认并进入当前回合的追加消息缓冲区 |
| `injected` | 在 AgentLoop 的下一次模型请求边界注入上下文 |
| `queued` | 当前回合已经收口，追加消息降级为下一条 FIFO 回合；同时带 `queue_turn_id` 和 `degraded_from: "steer"` |
| `failed` | 回合取消、发生错误、等待审批或队列已满，追加消息未被处理 |

追加消息不会强行中断正在进行的模型 HTTP 请求、工具执行或 shell 子进程，也不会触发额外的模型摘要请求。服务端只在 AgentLoop 安全边界读取并注入；审批等待期间请求直接返回冲突，由前端保留原文供用户重新编辑或发送。

`turn.queued` 表示用户消息已完成持久化，但当前会话已有回合或 AgentRuntime 正在恢复；payload 包含 `query`、FIFO `position` 和 `mode: "queue"`。该事件不启动新的模型请求，队列中的回合会在前一个回合完成后自动产生 `turn.started`。排队消息可以在当前回合执行期间继续提交，取消排队项会产生 `turn.cancel.requested` 和 `turn.cancelled`，不会影响正在执行的回合。

`turn.started.payload.attachments` 保存规范化后的附件元数据；图片和视频可带受长度限制的 `preview_url`（JPEG/PNG/WebP data URL），用于历史回放恢复压缩缩略图。旧 journal 没有该字段时，renderer 会通过 Electron 仅对工作区 `.desktop-attachments` 中仍存在的源文件补建缩略图；源文件已移除则仅显示附件名称。

`turn.cancel.requested` 的 payload 至少包含 `turn_id`，并在当前回合存在 Team 成员时附带 `team_members: string[]`。该列表是取消请求发出时仍登记为活跃、且尚未回传结果的真实成员名称，前端可据此显示停止范围。

`video.progress` 描述单个视频附件的预处理和理解阶段，payload 包含 `attachment`、`stage`、`status` 和用户可读的 `message`；模型阶段会附带实际 `model`，抽帧时附带 `completed`、`total`，命中分析结果缓存时附带 `cache_hit: true`。发送给视频模型的原视频多模态 block 会使用配置的 `fps`（由 `DESKTOP_VIDEO_INPUT_FPS` 控制）。阶段包括 `validating`、`inspecting`、`uploading`（COS 可选路径）、`extracting_frames`、`preparing_payload`、`analyzing` 和 `completed`。`video.failed` 使用相同的附件字段，并附带稳定的 `error_code` 与 `message`；当前错误码包括 `ffmpeg_missing`、`source_missing`、`unsupported_codec`、`inspection_failed`、`frame_extraction_failed`、`payload_too_large` 和 `cancelled`。取消在 ffmpeg/ffprobe 处理边界终止子进程，并由回合终态事件收口。

`video.analysis` 是内部持久化交接事件，payload 包含 `attachment`、`model` 和第一阶段返回的 `analysis` 文本。会话恢复时使用该文本重建 Agent 上下文，不重新注入 Base64 视频；旧回合没有该事件时仅恢复原问题和不可用提示。

视频回合采用确定性分流：意图判断在第一阶段视频模型调用前完成。普通视频问答、描述、总结或事实判断由视频模型分析后直接作为最终答复，发出 `assistant.message(phase=final)` 和 `turn.completed(reason=video_answer)`，不进入工具循环；明确要求修改项目、读写文件、运行命令或调用工具时，第一阶段完成视频理解后，再把分析结果交给主 Agent 模型，继续执行终端、MCP、RAG 等完整工具循环。当前不会因附件自动切换模型；不支持视频的模型会返回明确提示。当前版本明确拒绝多视频附件。

视频缓存分层保存：统一用户目录下对应 workspace 的 `BUFFEED_HOME/workspaces/<workspace-hash>/video-cache/analysis/<源文件指纹>/` 保存关键帧清单和分析结果，按 `DESKTOP_VIDEO_ANALYSIS_CACHE_MAX_AGE_DAYS`（默认 30 天）及 `DESKTOP_VIDEO_ANALYSIS_CACHE_MAX_BYTES`（默认 1 GiB）在视频处理前清理；Electron 用户数据目录 `video-preview-cache/` 保存 Chromium 预览转码结果，按 `DESKTOP_VIDEO_PREVIEW_CACHE_MAX_AGE_DAYS`（默认 14 天）及 `DESKTOP_VIDEO_PREVIEW_CACHE_MAX_BYTES`（默认 1 GiB）在 desktop 启动时清理。清理不会触碰原始附件、输入框缩略图或仍在使用的预览内容。

Lead 停止采用 cooperative cancellation：没有活跃成员时只设置 Lead 的取消事件；Lead 会在当前模型 HTTP、shell 或 MCP 调用返回后停止，并向用户追加一条最终摘要，说明 Lead 已完成内容和本回合代码变更。有活跃成员时，服务端为尚未回传结果的成员设置取消事件，并发送 `shutdown_request` 作为协议通知。成员的取消监听器会立即读取最近安全进度，先写入 `run.progress(phase=cancel.reported)`，payload 带 `status: cancelled`、`task_id`、`tool_name`、`in_flight` 和最后安全进度摘要，同时向 Lead mailbox 发送带 `status: cancelled`、`partial: true` 的 `result`；当前模型/工具动作返回后不再开始下一步，随后写入 `run.failed(error_code=cancelled)` 并退出。已经向 Lead 回传完整 `result` 的成员不再接受这次停止请求，并继续写入自己的 `run.completed`。Lead 会汇总已收到的成员取消报告、Lead 进度和代码变更，再向用户回复“已停止”；已经发出的模型 HTTP 请求和 shell 子进程不会被强制杀死，若成员动作仍未返回则在摘要中标记为待补发报告。

成员邮箱按本次 `run_id` 使用独立 mailbox key 路由，显示名称只用于协议寻址。上一回合残留的 `shutdown_request` 不会被同名的新成员读取；关闭消息仍只作用于发送它的那次成员运行。

## 当前已落地的只读快照

`GET /api/v1/sessions/{session_id}/team` 返回 SQLite journal 折叠出的 `schema_version=2` 快照，来源必须是明确的 `run.plan` 与后续 `run.*` 事件。API 已检查 durable journal 时，即使当前 execution 没有事件也返回 `available=false`，不会回退到任务文件并虚构 lead/成员节点；旧 `schema_version=1` 兼容投影只保留给显式传入 `team_events=None` 的旧调用方。两种快照都标记 `read_only=true`，前端只渲染真实任务、owner、依赖和成员，不根据普通工具调用创建节点。没有数据时 `available=false`，不显示空画布。

Team 图边是结构关系而不是生命周期事件节点：`run.plan` 会为真实 lead 到成员声明 `delegate` 边，并为成员到其分配任务声明 `owner` 边；任务依赖仍使用 `depends_on`/`dependency`，生命周期事件只有在 payload 明确提供 `parent_run_id`、`continues_run_id` 或 `edge` 时才追加 `delegate`、`continuation` 或其他执行流边。前端时间线与画布互补，点击事件会选中其真实成员/任务并高亮关联边。

Team 复杂布局由 renderer 的 ReactFlow 画布和 ELK layered 布局器负责。ReactFlow/ELK 只处理节点定位、缩放、平移、只读选择和关系线渲染，不写入 Team 状态，也不在后端保存布局结果。画布输入仍严格来自当前 `execution_id` 的 `run.plan` 及后续 `run.*` durable 事件投影；成员委派、成员任务归属、任务依赖、显式接续/执行流和未知边类型都会参与多层布局，普通工具事件不会被推断为 Team 节点或边。

Lead 的 `run.completed` 或 `run.failed` 是当前 execution 的收口边界。desktop 在用户点击停止时请求停止尚未回传结果的成员；在成员自己的取消报告或终态事件尚未回放前，projection 将未终态成员标为 `cancelled`，并按成员/lead 结果收口未终态任务。Lead 的取消摘要会作为当前回合的最终 `assistant.message` 和 `turn.finished.payload.cancellation` 持久化，历史回放可以直接显示，不依赖后续工作树状态。后续真实的 `run.completed`/`run.failed` 仍可覆盖临时的取消状态，不强制杀死模型 HTTP 或 shell 子进程。

Team `run.plan` 只包含当前 execution 创建的任务。历史 workspace 状态文件继续保留供任务系统使用，但不会重新注入新的 Team 计划或画布；当前 execution 新建任务时会追加一份更新后的 `run.plan`，保证成员和任务在真实创建顺序下都能回放。

`GET /api/v1/sessions/{session_id}/team/events?after=<cursor>&execution_id=<id>` 返回 Team 事件增量和从完整 journal 重放得到的快照。`execution_id` 用于隔离不同 turn 的 Team run；事件增量与 SSE 共用同一个 session cursor，不以时间戳补偿缺失事件。

运行时冷恢复时会从已落盘的 `run.plan` 重建 `run_id→execution_id` 索引和最近 execution 指针，迟到的成员终态仍归属于原回合，不会按当前 active turn 猜测。

Team 增量响应中的 `snapshot.events` 保留当前 execution 最近 100 条事件，renderer 可以在重连后恢复时间线而不依赖内存状态。

每个真实 `run.plan` 都会在 Agent API journal 中补记 lead 的 `run.started`；lead 的模型/工具阶段映射为 `run.progress`，回合完成、失败或取消分别落为 `run.completed`/`run.failed`。计划生产者即使没有把 lead 列在 `members` 中，API 也会补齐这段生命周期，但不会凭空添加任务节点。execution 以 turn 隔离；普通 Agent turn 不会覆盖最近一次已经落盘的 Team execution。

RAG `GET /api/v1/rag/tasks/{task_id}` 返回 `task`、`events`、`children` 和可选 `page_routing`；任务终态包括 `vector_ready` 与 `graph_ready`，桌面端在任一终态停止轮询。`page_routing` 的扩展 provenance 字段可以缺省，以兼容历史 manifest。

## Team 事件最小集合

以下 durable 事件由 `apps/agent-runtime/team_events.py` 校验并进入 Agent API 的 SQLite journal；Buffeed teammate 生命周期通过显式 sink 产生这些事件：

| 事件 | 必要字段 | 作用 |
| --- | --- | --- |
| `run.plan` | `execution_id`、`members`、`tasks`、`edges`（可带产生该计划的 `run_id`） | 声明真实成员、任务、依赖和委派关系；`run_id` 用于迟到计划的 execution 归属 |
| `run.started` | `execution_id`、`run_id` | 成员开始执行 |
| `run.progress` | `run_id`、`phase`、`summary` | 更新成员当前状态 |
| `run.completed` | `run_id`、`duration_ms` | 成员完成；成员任务可附带 `task_id`、`result` 和 `result_format` |
| `run.failed` | `run_id`、`error_code`、`message` | 成员失败 |

成员取消时的 `run.progress(phase=cancel.reported)` 是停止汇报边界；其 payload 还应包含 `status: cancelled`、`task_id`、`tool_name`（可空）、`in_flight` 和最后安全进度 `summary`。对应的 mailbox `result` 带 `partial: true`，表示这是中间结果，不得被投影为任务完成。

`edges[].kind` 的常用值为 `owner`（成员负责任务）、`depends_on`/`dependency`（任务依赖）、`delegate`（父 run 委派子 run）、`continuation`（前一 run 接续到后一 run）和 `execution-flow`（显式执行流）。未知值必须原样保留，旧客户端可以按普通结构边降级渲染。

Team 任务协调遵循成员优先的依赖屏障：任务可通过 `assignee`、`assigned_run_id` 和 `assigned_at` 绑定到成员。Lead 可以继续执行不依赖这些任务的工作，但不得认领已分配给成员的任务。成员完成后，`run.completed` 可附带 `task_id` 和 `result`；只有该结果被 Lead 通过 `await_team_result` 收到后，依赖任务才应继续执行。

成员结果使用 `result_format: "team-check-v1"` 的 JSON 字符串。报告包含版本、任务标识、短摘要、从 `run.started` 到完成期间累积的 `checks`（阶段、状态、必要输入摘要和输出预览）、耗时和可选的 `final_message`，不依赖成员最后一条文本。成员 mailbox、任务结果缓存和 `run.completed.payload.result` 使用同一份报告；后者写入本会话 SQLite durable journal，runtime 冷启动时从 journal 重建结果缓存。这样 Lead 重启后仍能通过 `await_team_result` 读取已完成结果，Team 画布也能回放该结果。

`await_team_result` 默认使用有限等待时间，由 `BUFFEED_TEAM_RESULT_TIMEOUT_SECONDS` 配置（默认 300 秒，传入正数可覆盖）。超时返回 `status: "timeout"` 及每个未完成任务的状态、成员、耗时和接管资格；不会自动完成或接管成员任务。超过成员宽限期时仍优先返回 `status: "takeover_available"`，Lead 必须先检查并显式调用 `takeover_task`。

成员至少拥有 5 分钟（300 秒）宽限期。`inspect_team_tasks` 是只读检查，返回成员任务耗时和 `takeover_allowed`；超过宽限期后，Lead 必须显式调用 `takeover_task` 才能接管任务。接管会清除成员分配并恢复为待认领状态，同时产生 Lead 的 `run.progress(phase=task.takeover)`。系统不会在超时后自动伪造成员完成，也不会强制中断成员正在进行的模型请求或工具调用。

兼容规则：没有 `run.plan` 的普通 turn 不生成团队节点；前端和后端都只 `fold` 显式 Team 事件得到执行状态，再投影到聊天和画布，禁止画布自己从工具事件猜成员。Team 写工具默认未向 desktop API 开放，只有显式环境开关才启用。

## 回放要求

- event id 在单个 session 内单调递增。
- 结构事件必须可从持久化 journal 重放。
- 未知事件类型应保留在日志中，但不能阻塞旧客户端。
- 事件契约变更时同时更新前端类型、fixture 和本文件。
